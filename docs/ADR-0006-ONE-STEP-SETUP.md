# ADR-0006：单路径环境准备与可恢复安装

- 状态：已接受
- 日期：2026-08-09

## 背景

AgentDeck 已能检测 Termux、RUN_COMMAND、`allow-external-apps`、proot-distro、Ubuntu、Codex、认证和 wrapper，也能按配方依赖执行“探测、安装、再验证”。但检测在设置页、安装在工具页、认证在 Termux，用户需要自己判断下一步。长安装只返回最终结果，离开页面后缺少稳定的任务状态，重复点击还可能启动并发安装。

## 决策

1. 以一份应用级 `SetupState` 统一环境报告、扫描状态、安装阶段、错误和下一步动作。设置页、工具页、首次准备页和对话页只消费这份状态，不各自维护安装真相。
2. `SetupActionResolver` 按固定依赖顺序给出唯一主动作：安装 Termux、授予权限、启用外部调用、安装 Codex 环境、检测或配置 Codex 认证、开始对话。认证探针优先复用已有账号、API Key 或 Provider `env_key`，不会默认要求重复登录。内部 recipe ID、优先级和命令日志不进入主流程。
3. Codex 环境安装仍由受校验的 APK 配方驱动。安装器对依赖逐项报告探测、安装、验证和完成阶段，不伪造下载百分比。
4. 安装命令使用 Termux `$HOME/.agentdeck` 下的原子目录锁。活动安装拒绝第二个安装命令；异常退出后允许安全回收仅含 PID 的陈旧锁。固定锁路径不接受用户输入。
5. `SetupCoordinator` 使用应用生命周期作用域，页面切换不取消安装。进程重建后不信任旧的“安装中”UI，而是重新运行幂等 Doctor；配方探测决定继续、跳过或重试。
6. Termux 安装、Android 权限、`allow-external-apps` 和缺失时的 Codex 认证仍保留必要的用户确认。AgentDeck 负责把当前动作合并成一个按钮，并在用户返回前台时自动复检。
7. 安装成功必须以最终 Doctor 为准；Intent 被系统接受、脚本退出或下载完成均不能单独代表环境可用。

## 后果

- 已安装环境直接显示就绪，不再出现误导性的“安装 / 修复”。
- 用户不需要理解 proot、recipe 依赖或手工输入 `apt`/下载命令。
- Termux 后台任务无法被 Android 进程可靠取消，因此安装必须保持幂等并用锁防止重复；取消能力留待本地桥接进程阶段实现。
- 真机仍需覆盖首次安装、返回前台、网络失败、App 进程重建和陈旧锁恢复。
